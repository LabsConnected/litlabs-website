The voice code already implements the architecture the operator specified:

| Concern | Implementation |
|---------|---------------|
| Single guarded microphone entry point | `requestMicrophoneStart({ source })` in `VoiceSessionContext.tsx` |
| Source label enum | `composer_mic_click \| floating_voice_button \| hands_free_resume \| mount_effect \| tts_started \| tts_finished \| session_connected \| store_hydration \| unknown` |
| Block unauthorized sources | `if (!isExplicitGesture && !isHandsFreeResume) return;` |

### 4b. New `/api/system/capabilities` route (this turn)

`src/app/api/system/capabilities/route.ts` exports the `CapabilitySnapshot` type and a `GET` handler that probes (in parallel):

- **AI provider** via internal fetch to `/api/llm/health` (returns `ready | degraded | unavailable | unknown` based on Gemini/OpenRouter availability)
- **Autonomic loop** via parallel GETs to `/api/director/plan` and `/api/agent-tasks` (returns `healthy | degraded | offline | unknown`)
- **Voice / microphone** — the server returns `status: "unknown", microphone: "unavailable"` because the server **cannot** reliably know the local browser's microphone state. The client (VoiceSessionContext) must merge this with its own `voiceInputState`.
- **Project / workspace / terminal** — currently `status: "unknown"` with a clear reason. Probes for these require Clerk auth + Supabase project/workspace queries that are out of scope for this initial route.

**Truthful default:** when a probe fails or is not yet wired, the route returns `"unknown"` with a `reason` — never invents `ready` or `healthy`.
