fix: image generation pipeline — storage fallback, auto-quality fallback, quota error

Three issues were breaking image generation:

1. Gemini images were not persisted to durable storage. The handler
   returned a raw data:image/png;base64,... URL which can be several MB.
   Large data URLs break localStorage (history gets truncated) and
   cause "Failed to load image" in the <img> tag.

2. Auto-quality mode had no fallback when all quality providers failed.
   If Gemini quota was exhausted and FAL/Recraft were not configured,
   the user got a hard 502 with no recovery.

3. Gemini quota exhaustion (429) was reported as a generic
   "PROVIDER_ERROR" with no actionable guidance.

Fixes:
- Renamed persistToR2 → persistImage. Tries R2 first, then falls back
  to Supabase Storage (bucket: studio-images) when R2 is not configured.
  Returns a durable public URL instead of a fragile data URL.
- Added Gemini to the persistImage call list (was only alibaba/fal/
  openai/recraft).
- Added Pollinations as a last-resort fallback in auto-quality mode
  so users always get an image even when all paid providers are down.
- Detect 429 quota errors and return code "QUOTA_EXCEEDED" with an
  actionable message: "Try Auto Best (Free) mode which uses
  Pollinations — no API key needed."
